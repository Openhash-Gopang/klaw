1. hondi 인증 · 과금 연동 FEATURE

klaw #17, #20, #21 · hondi #274

배경 원칙(주피터 지시): "혼디 가입자는 혼디 시스템의 모든 모듈에 자유로이 접근할 수 있어야 한다 — hondi.net에 전화번호 인증하면 다른 모든 K-서비스에 자유로이 접근하고, hondi.net과 동일한 방식으로 사용량에 따른 GDC 차감이 이뤄져야 한다."

  • DeepSeek 무료 이용 경로 신설 — API Key를 직접 입력하지 않고 DeepSeek을 선택하면, K-서비스 공용 인증 모듈(k-service-auth-client.js, phone_verify_token 기반)로 로그인 후 /klaw/relay(K-Law 공유 계정)를 통해 이용. 본인 API Key 입력 시(BYOK)는 기존처럼 브라우저에서 각 제공사 API로 직접 호출 — relay를 거치지 않음.
  • 인증 필수화 — _klawCall이 요청 전 반드시 KAuth.ensureLogin()을 거치도록 변경. 이전엔 401을 받은 뒤에야 재로그인하는 반응형 구조였음.
  • 실제 로그인 상태 배지 — 헤더의 "게스트" 표시가 2026-07-23 제거된 구 고팡 지갑 SSO 콜백(_onGopangAuth) 잔재라 실제 상태와 무관하게 고정 표시되던 문제를 발견, KAuth.hasValidLogin() 기반 실시간 배지(_klawRefreshAuthBadge)로 교체.

2. 토큰 예산 · 안정성 FIX

klaw #18, #22, #25, #31, #32

핵심 발견: klaw-pro 티어는 DeepSeek의 "thinking"(추론) 모드가 항상 켜져 있고 (hondi worker.js payload.thinking), 추론 토큰도 max_tokens 예산에서 함께 소모된다. 예산이 부족하면 모델이 추론만 하다 실제 답변은 한 글자도 못 쓰고 끝나는 사례가 반복 발견됨.

STEP A·B가 특히 높은 이유: 각 STEP은 이전 STEP 전체 출력을 컨텍스트로 이어받아 갈수록 입력이 커지고, 요구되는 실제 출력 분량도 STEP C(확신도 숫자+짧은 요약)보다 훨씬 길다.

자동 복구 로직

  • _klawCaseIsComplex() — 글자 수(900자) 또는 당사자 키워드 빈도(12개 초과) 기준으로 복잡한 사건을 판정해 klaw-flash 대신 klaw-pro로 자동 승격.
  • flash→pro 자동 재시도 — klaw-flash 응답이 finish_reason:'length'로 잘리면, klaw-pro로 한 번 자동 재시도(사전 복잡도 판정을 놓친 사례 사후 구제).
  • 빈 결과 안전장치 — 사건 분석 핵심 3필드(사건의 개요/원고 주장/피고 주장)가 전부 비거나, STEP 결과가 완전히 빈 문자열이면, 더 큰 예산으로 1회 자동 재시도 → 그래도 비면 "성공한 것처럼 보이는 빈 결과"를 조용히 넘기지 않고 명확한 오류 + "다시 시도" 버튼 표시.
  • 종합 확신도 파싱 견고화 — 모델이 [종합 확신도: min(8,9)=8/10]처럼 계산식을 적어도 마지막 숫자를 정확히 추출하도록 정규식 보완.

3. 이력 기능 확장 FEATURE SECURITY

klaw #21, #34, #35 · hondi #274, #278, #280

3-1. 본인 전용 + 프라이버시 (#21)

기존 이력 기능은 currentUser?.ipv6(2026-07-23 제거된 죽은 코드가 채워야 하는 값)에 의존해 저장·조회가 항상 조용히 실패하고 있었다. 게다가 백엔드가 클라이언트가 보내는 user_id를 그대로 신뢰해, 값만 바꾸면 남의 이력을 보거나 남의 이름으로 기록을 남길 수 있는 취약점 발견.

  • hondi worker.js: /klaw/sessions/*가 phone_verify_token으로 서버가 guid를 직접 재확인 — 클라이언트가 보내는 user_id는 완전히 무시.
  • klaw: 이력 목록을 일치도 % + 시각 두 항목만 표시하도록 단순화(주피터 지시 — "일치도 점수만 표시").
  • PocketBase klaw_sessions에 match_rate 필드 신설(마이그레이션/Admin API로 무중단 반영).

3-2. 전문 저장 · 열람 (#34, #35)

"일치도만 표시"에서 한 발 나아가, STEP 0~C 판결문 전문을 저장하고 이력 목록 클릭 시 모달로 다시 열람하는 기능 추가.

  • GitHub 저장 방식은 채택하지 않음 — klaw 저장소가 공개 저장소라 인증 없이 전 세계에 노출되고, 매 시뮬레이션마다 커밋이 쌓여 GitHub Pages가 재배포되는 문제가 있어 기각. 대신 이미 인증 구조가 갖춰진 PocketBase에 필드만 추가하는 방식 채택.
  • hondi worker.js: /klaw/sessions 저장 시 verdict_full 함께 저장. /klaw/sessions/detail(신규) — record id + phone_verify_token으로 조회, 레코드의 user_id가 요청자 guid와 정확히 일치할 때만 반환(안 맞으면 404 — 존재 여부조차 안 알려줌).
  • PocketBase에 verdict_full 텍스트 필드(최대 200,000자) 신설.
  • klaw: 이력 행 클릭 → 모달에 사건 종류·사건 개요·주문·판결 요약 메타 정보 + 전문 표시. 토큰 만료 시 _klawCall과 동일한 재로그인 자동복구 로직 적용.

klaw #15

6. 사고실험으로 발견한 문제들

코드를 실제로 추적하며 발견 → 즉시 수정한 항목들
구 SSO 죽은 코드 — _onGopangAuth/currentUser가 2026-07-23 제거된 인증 스크립트를 전제로 작성되어 있어, 이력 저장·조회·헤더 배지가 전부 "성공한 것처럼 보이지만 실제로는 항상 실패"하는 상태였다. 에러가 안 나서 오래 발견되지 않았을 가능성.
user_id 신뢰 취약점 — /klaw/sessions/*가 클라이언트가 보내는 user_id를 검증 없이 사용해, 값만 바꾸면 타인의 사건 요약·판결 내용을 조회하거나 타인 명의로 기록을 남길 수 있었다.
thinking 모드 토큰 소모 — max_tokens를 여러 차례 올려도 계속 잘리는 근본 원인이 "추론 토큰도 같은 예산을 먹는다"는 것이었음을 worker.js 코드 확인 후에야 발견. 이전 시도들은 증상(잘림)만 완화했을 뿐 원인을 못 잡았었다.
STEP별 예산 불균형 — 모든 STEP에 동일 예산(9000)을 줬을 때 STEP 0·C는 성공, STEP A·B만 실패하는 실사용 로그를 근거로 STEP별 차등 예산 필요성 확인.
이력 전문 저장 시 4가지 허점 — ① 저장 상한(60,000자)이 최악의 경우(STEP 예산 총합 48,000토큰) 대비 부족 + 무음 절단 → 200,000자 상향 + 명시적 절단 표시. ② 상세 모달에 사건 맥락(종류/개요/주문/요약)이 안 보임 → 표시 추가. ③ 토큰 만료 시 재로그인 미지원 → _klawCall과 동일한 자동복구 적용. ④ KAuth 미정의 방어 누락 → 추가.
patch 배포 사고 2건 — (a) 색상 통일 patch가 그 사이 merge된 다른 patch와 컨텍스트가 어긋나 git am이 반복 실패(원인: CRLF 정규화 이전 상태 기준으로 만들어졌던 patch). (b) 보완 전 원본 patch(#34)가 먼저 merge되어, 4가지 허점 보완판을 현재 head 기준으로 다시 만들어 별도 PR(#35)로 반영.

7. 알려진 제약 · 남은 과제

  • 근본적 한계 — STEP별 maxTokens를 계속 올리는 건 "숫자 땜질"이라는 한계가 있다. 더 구조적인 해법은 (1) 이전 STEP 전체 출력을 그대로 이어붙이지 않고 요약해서 컨텍스트를 줄이거나, (2) finish_reason:'length' 발생 시 "이어서 계속 작성" 요청을 자동으로 보내 이어붙이는 방식일 것 — 둘 다 별도 설계가 필요한 큰 작업으로 남겨둠.
  • K-Law 전용 발급 키 없을 시 공용 DEEPSEEK_API_KEY로 폴백하는 공유 계정 구조상, 무료 경로 사용량이 늘면 하루 예산(1인 300원/계정 전체 30,000원) 소진이 더 빨라질 수 있다 — thinking 모드 토큰 상향과 트레이드오프 관계.
  • .caution-bar(동적 경고 메시지 스타일)는 이번 청색 통일 작업에서 의도적으로 제외 — 정적 안내 박스 묶음과 성격이 달라 보여서. 필요 시 후속 작업으로 통일 가능.
  • 대법원 종합법률정보 예시 링크(portal.scourt.go.kr)가 특정 판례 하나를 가리키는 고정 링크라, 시간이 지나면 "최신 판례" 취지와 안 맞을 수 있음 — 주기적 갱신 필요.
